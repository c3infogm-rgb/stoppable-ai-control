# 通常のレビューと制御条件ギャップチェックの違い

## 目的

この文書は、制御条件ギャップチェックが「通常のレビューより優れている」と主張するためのものではありません。

同じ対象を見ても、**問い・出力・次工程が異なる**ことを説明するための公開用比較です。

この比較構造は、実際に行った内部の第三者ソフトウェア検証をもとに一般化しています。第三者製品固有の識別情報、再現手順、未公開のfinding、Responsible Disclosure対象情報はここでは公開しません。

## 同じ対象を見ても、問いが違う

| | 通常寄りの防御レビュー | 制御条件ギャップチェック |
|---|---|---|
| 対象 | 同じ対象版・同じソース束を読む | 同じ対象版をControl単位で固定する |
| 主な問い | 実装上、問題になり得る箇所はあるか | 宣言したControlは、条件を変えても維持されるか |
| 出発点 | source / configuration / control flow | Declared Control / Baseline / Comparator |
| 発見物 | candidate / concern / review finding | Replay可能なVariantとObservation |
| 作用境界 | 必要に応じてレビューで記述 | Effect Boundaryを明示的に分ける |
| 条件変更 | 必須ではない | Variantとして宣言して比較する |
| 未観測 | レビュー記述に含め得る | UNOBSERVEDとして結果から分離する |
| 証拠不足 | レビュー判断で保留し得る | UNDEFINEDとしてPASSへ寄せない |
| 次工程 | 修正・追加調査・テスト | Replay → Boundary inference → Operating Envelope候補 |

## 実際の内部Referenceで起きたこと

通常寄りの防御的なソースレビューでも、**事前拒否の判断と、その後のイベント処理が同じ停止保証になっているか**という候補地点には到達しました。

つまり、

```text
通常レビュー
    ↓
「拒否判断と作用停止の契約を確認した方がよい」
    ↓
candidate
```

という発見自体は、通常のレビューでも可能です。

その後、制御条件ギャップチェックの方法論では、同じ問題領域を次のように分解しました。

```text
Declared Control
    ↓
Control Path
    ↓
Effect Boundary
    ↓
Comparator
    ↓
Variant Axis
    ↓
Replay / Observation
```

方法論支援レビューでは、少なくとも次を別々に扱いました。

- 制御がどこまで適用されるか
- 拒否や停止がどの機構で成立するか
- エラーや結果がどのように伝達されるか
- 実作用が起きなかったことを何の証拠で確認するか

**エラーが記録されたこと**と、**作用前に止まったこと**を同じ証拠として扱わない、という分離が重要でした。

## 「同じ条件で差を見る」をどう作るか

次の段階では、同じ対象版・同じ制御目的を維持したまま、制御に関係する条件だけを変えるVariantを設計しました。

公開用に抽象化すると、構造は次の3つです。

```text
A. 製品既定の制御経路
   ↓
   既定条件で観測

B. 制御側を先に評価する条件
   ↓
   順序だけを変えて観測

C. true short-circuit reference
   ↓
   拒否なら作用側へ渡さないmechanism control
```

ここで重要なのは、最初から「Aが危険」「Bなら安全」と決めないことです。

結果が変わった場合だけ、その変化をBoundary候補として追加Replayします。結果が変わらなければ、回数を増やして境界があるように見せません。

```text
条件差でObservationが変わる
        ↓
Boundary candidate
        ↓
必要な隣接Variantだけ再Replay

条件差でObservationが変わらない
        ↓
その軸ではBoundary未観測
```

## 何が差なのか

差は「普通のテストでは見つからない問題を必ず見つける」ことではありません。

```text
通常レビュー
= 問題候補を発見・説明する

制御条件ギャップチェック
= 候補を、条件を変えて反証可能なControl実験へ変換する
```

という出力構造の違いです。

そのため、通常の単体テスト、統合テスト、探索的テスト、静的解析、脆弱性診断、コードレビューを置き換えません。

## この比較から言えないこと

この内部Referenceは、同一sourceを使った比較材料ではありますが、厳密な性能ベンチマークではありません。

したがって、次は主張しません。

- C³方法論で発見率が何%上がる
- 通常レビューでは同じ候補を発見できない
- 13軸を使えばすべてのGapを発見できる
- Sequenceを変えれば必ずBoundaryが出る
- 1回のReplayでBoundaryを確定できる
- この比較だけで第三者製品の脆弱性を確定できる

厳密なA/B性能比較を行う場合は、同一source、同一model、同一time/token budget、blind条件、事前固定した評価基準が別途必要です。

## 公開6ケースとの関係

この考え方を一般化して公開しているのが、現在の6ケースです。

- AUTHORITY
- TIMING
- TARGET
- RETRY_RECOVERY
- SEQUENCE
- ENFORCEMENT_PLACEMENT

正式な非公開検査では、これを13軸の候補空間へ広げ、対象に応じて適用軸を選びます。
